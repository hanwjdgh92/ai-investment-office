# 매매일지(Trading Journal) 웹앱 Design Spec

**작성일:** 2026-08-18
**배경:** 사용자가 실제로 체결한 크립토 매매 내역(매수/매도)을 직접 기록하고, 손익/승률을 자동 계산해
보고 싶어함. 기존 AI 투자 오피스(`office/`)는 AI 분석 리포트용이고 사용자의 실제 매매 기록과는
무관하므로, 완전히 별도의 로컬 전용 웹앱으로 만든다.

## 목표

- 사용자가 실제로 체결한 크립토 매매 1건씩(종목/매수·매도/가격/수량/날짜/메모/차트사진)을 기록·조회·삭제.
- 같은 종목의 매수→매도를 FIFO로 자동 매칭해 거래별 손익, 전체 승률/총손익을 계산.
- 내 PC에서만 사용(다른 기기/외부 접근 불필요).

## 범위 밖 (Non-goals)

- 국내주식/해외주식 매매 기록 — 이번 범위는 크립토만.
- AI 시그널(Trigger 등)과의 연동/비교 — 순수 사용자 수기 기록.
- 외부 접근, 인증, 다중 사용자, 클라우드 동기화.
- 이미지 리사이즈/압축 — 원본 그대로 저장.

## 아키텍처

- 서버 코드 없음. `trading-journal/index.html` + `app.js` + `style.css` 정적 파일 3개로 구성된
  단일 페이지 앱.
- 데이터는 브라우저 내장 IndexedDB(`trading_journal` DB, `trades` object store)에 저장. 차트사진은
  Blob으로 그대로 저장(별도 base64 인코딩 없이 object store에 직접 저장).
- 실행: `trading-journal/launch.bat`이 `python -m http.server 8788 --directory trading-journal`을
  실행하고 `http://127.0.0.1:8788`을 기본 브라우저로 연다. 커스텀 서버 코드를 작성하지 않고 Python
  표준 라이브러리 내장 명령을 그대로 씀 — file://로 직접 열면 Chrome이 보안 정책상 IndexedDB를
  차단하므로 http:// origin으로 띄우는 용도만.

## 데이터 모델

`trades` object store, `id`를 keyPath로 auto-increment:

| 필드 | 타입 | 필수 | 설명 |
|---|---|---|---|
| id | number | auto | PK |
| symbol | string | Y | 대문자 정규화(예: "BTC") |
| side | "buy" \| "sell" | Y | |
| price | number | Y | 양수만 |
| quantity | number | Y | 양수만 |
| date | string (YYYY-MM-DD) | Y | |
| memo | string | N | 자유 텍스트 |
| chartImage | Blob | N | optional |
| createdAt | number (timestamp) | auto | 정렬용 |

symbol 필드에 인덱스 생성(필터용).

## FIFO 손익 매칭 로직

- 전체 거래를 symbol별로 그룹핑 후 date/createdAt 오름차순 정렬.
- symbol마다 buy 큐(FIFO)를 유지: buy 레코드를 만나면 큐에 `{price, remainingQty, tradeId}`로 push.
- sell 레코드를 만나면 큐 앞에서부터 수량을 차감하며 매칭 쌍 생성:
  - 매칭 쌍마다 `matchedQty = min(sell 잔량, buy 큐 head 잔량)`
  - `pnl = (sell.price - buy.price) * matchedQty`
  - buy 큐 head의 remainingQty를 차감, 0이 되면 큐에서 제거
  - sell 잔량이 남아있으면 다음 buy로 계속 매칭(매수 여러 건에 걸친 분할 매칭 지원)
  - sell 수량이 buy 큐 전체보다 많으면(매도 초과분) 매칭 없이 무시하고 콘솔 경고만 남김(공매도 미지원,
    사용자 입력 실수로 간주)
- 매칭 안 된 buy 잔량(큐에 남은 것) = "보유중"으로 심볼별 합산해 통계 카드에 표시, 손익 계산에서 제외.
- 전체 통계: 총손익(모든 매칭 쌍 pnl 합), 승률(pnl > 0인 매칭 쌍 수 / 전체 매칭 쌍 수), 총 매칭 횟수.
- 이 계산은 저장하지 않고 화면 렌더링 시점에 전체 거래를 읽어 매번 다시 계산(거래량이 적어 개인용
  규모에서 성능 문제 없음).

## 화면 구성

1. **입력 폼** (상단): 종목/매수·매도 라디오/가격/수량/날짜(기본값 오늘)/메모(textarea)/차트사진
   업로드(`<input type="file" accept="image/*">`) + 추가 버튼.
2. **통계 카드**: 총손익, 승률, 총 매칭 횟수, 심볼별 보유중 수량 목록.
3. **거래 목록 테이블**: 최신순(createdAt desc). 컬럼: 날짜/종목/구분/가격/수량/메모 미리보기(말줄임).
   행 클릭 시 상세 패널(메모 전문 + 차트사진 원본 크기) 토글. 각 행에 삭제 버튼.
4. **종목 필터**: 드롭다운(전체 + 등록된 symbol 목록), 선택 시 목록/통계 모두 해당 종목만.
5. **백업**: "내보내기" 버튼 — 전체 레코드를 JSON(이미지는 base64 data URL로 변환)으로 다운로드.
   "가져오기" 버튼 — JSON 파일 선택 시 파싱해 object store에 복원(기존 데이터에 추가, 덮어쓰지 않음).

## 에러 처리 / 알려진 한계

- 필수 필드(종목/구분/가격/수량/날짜) 누락 시 저장 막고 입력 폼 아래 인라인 에러 메시지.
- 가격/수량이 0 이하거나 숫자가 아니면 같은 방식으로 막음.
- 삭제는 `confirm()` 팝업 후 즉시 반영(되돌리기 없음).
- 공매도(보유량보다 많은 매도) 입력은 막지 않고 저장은 되지만, FIFO 매칭에서 초과분은 무시됨 — 사용자가
  실수로 잘못된 매도를 입력해도 앱이 죽지 않게 하기 위함(§FIFO 매칭 로직 참고).
- IndexedDB는 브라우저(프로필) 종속 — 브라우저 데이터를 지우면 유실. 백업 기능으로 완화하되, 자동
  백업/동기화는 범위 밖.
- Chrome 등에서 file://로 index.html을 직접 열면 IndexedDB가 막혀 있어 반드시 `launch.bat`으로
  http://localhost 경유 실행해야 함.

## 검증 방법 (자동 테스트 프레임워크 없음 — 수동 확인)

1. `launch.bat` 실행 → `http://127.0.0.1:8788`에서 앱이 뜨는지 확인.
2. BTC 매수 1건 + 같은 수량 매도 1건 입력 → 손익이 `(매도가-매수가)*수량`과 일치하는지 확인.
3. BTC 매수 2건(수량 각각 0.5) 후 매도 1건(수량 1) 입력 → 두 매수 건에 걸쳐 분할 매칭되고 손익 합이
   맞는지 확인.
4. 매수만 있고 매도 없는 종목이 "보유중"에 뜨고 통계(총손익/승률)에서는 빠지는지 확인.
5. 차트사진 첨부 후 목록에서 상세 열어 이미지가 원본대로 보이는지 확인.
6. 브라우저 완전 종료 후 `launch.bat` 재실행 → 기존 데이터가 그대로 남아있는지 확인(IndexedDB 영속성).
7. 내보내기로 JSON 다운로드 → 새 브라우저 프로필(또는 데이터 삭제 후)에서 가져오기 → 거래/이미지/메모
   모두 복원되는지 확인.
8. 필수 필드 비우고 저장 시도 → 에러 메시지 뜨고 저장 안 되는지 확인.
